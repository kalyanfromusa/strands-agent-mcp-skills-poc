Overview

ShopAssist is a customer-support assistant for a fictional online store. The PoC's real subject is the architecture: a domain-free agent, skills as runtime-loaded procedures, and access control enforced by AgentCore rather than by the model.

What the PoC is designed to demonstrate

  • Generic-agent pattern. Adding a skill changes behaviour with no code change and no new agent zip.
  • Rules live in tools, not prompts. Return eligibility is enforced server-side; create_return re-checks before writing.
  • Per-user access outside the agent. One agent, one Gateway, three users, three outcomes. A direct Gateway call with bob's token to create_return is denied.
  • Broad AgentCore coverage. Runtime (HTTP agent + MCP server), Gateway (Lambda + MCP targets), Identity (OAuth2 provider), Policy (Cedar).
  • Two delivery paths. Terraform and boto3, comparable side by side.

Request flow: "return the headphones from 1042"

  1. CLI calls Cognito InitiateAuth (USER_PASSWORD_AUTH, users client) and receives an access token carrying cognito:groups.
  2. CLI POSTs to /runtimes/ARN/invocations?qualifier=DEFAULT with Bearer token and a session-id header (≥33 chars) that selects the microVM.
  3. Runtime JWT authorizer checks the client and the cognito:groups claim; the Authorization header is allowlisted through to the agent.
  4. First call in the microVM: sync skills from S3, connect MCPClient, tools/list with the user's token (Cedar filters the list).
  5. Bedrock Converse with system prompt, skill list and tools. Model calls skills → returns-and-refunds; agent returns instructions plus resolved Gateway tool names.
  6. Model calls orders___check_return_eligibility; SkillBinding allows it because an active skill declares orders.
  7. Gateway: JWT authorizer, Cedar AuthorizeAction, invoke Lambda with the tool name in client context.
  8. Result returns through the Gateway to the model; final text goes back as {"response", "skills_used", "tools_used"}.

Session model. One Strands Agent per process, one microVM per session id. That gives per-session conversation memory without a memory store. The CLI persists one session id per user in .deploy/session-<user>.txt; --new-session starts a fresh one. Details and limits: Agent & Skills → Conversation memory.

Hybrid tool binding (SkillBinding)

Skills declare servers in metadata.mcp-servers and use plain tool names. The Gateway exposes <target>___<tool>. The plugin bridges the two:

HookBehaviour
AfterToolCallEvent on skillsAppends a [Tool binding] block: exact Gateway names for the declared servers, plus "Not available to the current user: …" for tools the caller lacks
BeforeToolCallEventA Gateway tool runs only if an activated skill declares its server; otherwise the call is cancelled with a hint naming the skill(s) to activate. Local tools always allowed
BeforeInvocationEventResets per-invocation skills_used/tools_used

  mcp-servers: "orders support"

... Call `check_return_eligibility` with the order id and sku ...

Startup validate_skills logs declared servers without tools and backticked names not on declared servers (INFO in passthrough mode, since per-user filtering makes gaps normal; WARNING otherwise).

Why the binding exists

Skills say create_return; the Gateway exposes orders___create_return, and which tools exist depends on the caller. Something has to bridge the two.

OptionWhat breaks
Full Gateway names in skillsSkills depend on target names; renaming a target or moving a tool means editing every skill
Plain names, model works out the mappingUsually works, not reliably: the model sometimes calls create_return as written and gets "unknown tool"
Plain names + resolver (SkillBinding)One plugin to maintain

1 · Binding text most value

Exact names at activation. Turns bob's missing create_return into "Not available to the current user", which gives the clean permission reply scenario b checks for.

2 · Pre-call check optional

Forces skill activation first, so the model follows the skill's steps. Limits each skill to its declared servers, which matters because skills change behaviour without code review.

3 · Validation and tracking

Startup logs catch typos in skill tool names. skills_used/tools_used feed the CLI line and demo_access.py.

Behaviour layer, not a security control. It runs inside the agent and guides the model. Cedar hides and denies tools per user (scenario d), and create_return re-checks eligibility server-side. Removing the binding wouldn't let bob do anything new.

Costs: three hooks tied to Strands' event API; part of the ~800–1,000 tokens added on activation; an occasional extra model call when a premature tool call is cancelled. Alternative: full Gateway names in skills plus a generic system-prompt rule for missing tools. That's simpler, but it couples skills to target names and makes the permission message depend on the model following a general rule.

Conversation memory

The agent remembers a conversation in process memory only. There is no memory store: the "memory" is the message history of one Strands Agent, kept alive because AgentCore Runtime gives each session its own microVM.

session id ──► microVM ──► app.py process ──► AgentRuntime ──► Agent
                                                               ├─ messages  (conversation history)
                                                               └─ state     (activated skills)
  1. The client picks the conversation. The CLI and chat UI send X-Amzn-Bedrock-AgentCore-Runtime-Session-Id (the CLI keeps one per user in .deploy/session-<user>.txt). The Runtime routes that id to the same microVM.
  2. One agent per process. get_runtime() holds one AgentRuntime, which holds one Strands Agent.
  3. Built once, then reused. The first message loads skills, connects to the Gateway and lists tools. _agent_for() returns the same object while the token sub stays the same.
  4. Strands keeps the history. agent(prompt) appends the user message, replies and tool results to agent.messages; the whole list goes to Bedrock on the next turn.
  5. Skill state carries over. Activated skills live in agent.state["agent_skills"], so follow-ups don't re-activate.
LimitEffect
Not persistedGone when the microVM ends (Runtime idle timeout or max lifetime; this repo uses the AWS defaults) or on redeploy

Changing user resets itA different token sub in the same process rebuilds the agent

Security & Access Control

Access is enforced outside the agent. The model can misbehave and still not reach a tool the caller isn't entitled to.

Source: docs/03-architecture.md § Per-user access control, Identity design, Security notes

Enforcement layers

1
Runtime inbound JWT authorizer + claim rule. Token must come from the users client and cognito:groups CONTAINS_ANY shop-admin, shop-viewer. carol stops here.
2

Implementation details worth scrutinising

Token plumbing across threads

bind_request_token() writes the token into a contextvar and a process-wide relay, because Strands' MCPClient runs on a background thread whose context was copied at start. The agent caches its tool list per token sub and rebuilds the MCP client and agent when the sub changes. Calls are serialised with a lock.

Header allowlist

requestHeaderAllowlist = ["Authorization"] on the agent runtime is what lets the token reach agent code. Without it the agent returns error: missing_authorization.

Cedar specifics

Principal type AgentCore::OAuthUser. JWT claims become string tags; arrays arrive as JSON text, so policies match with principal.getTag("cognito:groups") like "*\"shop-admin\"*". Actions are Gateway tool names. The viewer policy is an allow-list, so new tools are denied to viewers by default. Templates use {{GATEWAY_ARN}}/{{M2M_CLIENT_ID}} placeholders.

Creation ordering constraints

Cognito domain → credential provider (discovery needs token_endpoint). Policy engine → Gateway (with ENFORCE) → targets (support MCP runtime must be READY) → policies (CreatePolicy validates action names against Gateway tools).

SigV4 vs JWT

A runtime with a JWT authorizer doesn't accept SigV4, so the CLI calls the HTTPS invocation URL with a Bearer token directly.

Already in place

  • Trust policies use aws:SourceAccount/aws:SourceArn (confused-deputy guard); each role scoped to its own tables, zip and skills prefix.
  • S3 public access blocked; secrets in AgentCore-managed Secrets Manager; .deploy/ git-ignored.
  • Skills cannot name endpoints or credentials; binding blocks undeclared servers.
  • Independent proof: scripts/demo_access.py calls the Gateway directly with bob's token and expects a denial.

Delivery flow: zip vs container

Pipeline (.github/workflows/deploy.yml)

  1. Trigger: push to main touching agent, support MCP, common, skills, CI scripts, workflow, pyproject.toml or uv.lock; or manual dispatch.
  2. test: uv sync --frozen, pytest (offline, moto).
  3. build-and-push: matrix per image on ubuntu-24.04-arm, OIDC credentials, buildx linux/arm64, push :<sha> and :latest, GHA layer cache.
  4. deploy: verify images, s3 sync skills/, update support MCP runtime → SynchronizeGatewayTargets → update agent runtime (agent last, since its tool list comes from the Gateway).
  5. smoke (optional): demo_access.py --no-reseed --only b,c,d.

Rollout safety: "read, then update with everything the same"

UpdateAgentRuntime replaces the whole spec, so omitted optional fields reset. update_runtime_image.py reads the runtime and copies every updatable field (PRESERVED_FIELDS), replacing only agentRuntimeArtifact. A test fails if botocore adds an updatable field the script doesn't copy.

  • Refuses code→container switch without --allow-mode-switch.
  • No-op when already on that image (--force overrides); --dry-run available.

What moves the number

  • Longer conversations: input tokens grow with turns × calls per turn (full history re-sent).
  • Larger model via model_id.
  • Many long-lived parallel sessions held open on the Runtime.
  • Enabling Gateway semantic tool search (currently off).

Not implemented, possible savings: Bedrock prompt caching for system prompt and tool specs, shorter tool descriptions, fewer tools per skill.

Controls

  • 7-day log retention; log groups created up front.
  • On-demand only; network mode PUBLIC, so no NAT or VPC endpoints.
  • Optional account-wide $5 monthly budget, alerts at 80% actual and 100% forecasted.
  • project=shopassist tags on everything taggable; one-command destroy plus leftover checks.

Skill authoring rules

  1. No endpoints, URLs, credentials or <server>___<tool> names in skills. Declare servers; use plain names.
  2. A skill describes, the tool enforces.
  3. Folder name equals name.
  4. description is the trigger: say when to use and when not to.
  5. Plan for missing permissions.

Worked example: order-changes skill

Handles address changes and cancellations by checking order status with get_order and opening a high-priority ticket with create_ticket. No new tools. bob's binding marks create_ticket unavailable, so the agent reports order status and explains the permission gap.

uv run python scripts/local_gateway.py --port 8765
uv run python scripts/run_local.py --gateway-url http://localhost:8765/mcp \
  --prompt "Can I change the delivery address of order 1008? I'm C002 ..."
# then: terraform apply  |  infra/boto3/deploy.py   →   invoke_agent.py --new-session

Coupling points to keep in sync when adding a tool

  • TOOLS in handler.py ↔ tools_schema.json (guarded by test_schema_matches_tools)
  • viewer_read_only.cedar allow-list ↔ VIEWER_TOOLS in scripts/local_gateway.py (not test-guarded per docs)
  • Policy creation must follow target update (CreatePolicy validates action names)
  • Skill text references ↔ declared mcp-servers (startup log only)

Level 5 · Deployed browser chat with a real JWT

uv run python scripts/chat_ui.py --open                    # http://127.0.0.1:8790
uv run python scripts/chat_ui.py --print-token alice       # another terminal: prints alice's access token

Paste the token, click Use token, then chat or run a sample conversation. The page shows the token's username, groups, token_use, client_id and expiry, and warns about ID tokens, expired tokens, a foreign client id or a missing group. Restart chat_ui.py after a redeploy (it reads outputs.json at start).

Relay design. The Runtime doesn't answer CORS preflights, so chat_ui.py serves the page and relays messages. It binds to 127.0.0.1, refuses foreign Host/Origin headers, forwards only to the target fixed at start-up, and never logs or stores tokens.

Testing a new skill or tool

  1. Write the skill or tool. For tools: uv run pytest (schema/TOOLS parity), then update the Cedar viewer allow-list and VIEWER_TOOLS in local_gateway.py.
  2. Level 2 or 3 locally with both --role admin and --role viewer. Check the skills: / tools: line.
  3. Deploy (terraform apply or deploy.py). For a support MCP tool with Terraform, re-sync the Gateway target.
  4. Level 4 or 5 with --new-session; check the runtime log shows the new skill count.
  5. Level 6 to confirm the access matrix still passes.

Open questions (from the CI/CD patch)

  1. Pinned dependencies. requirements.txt uses >= ranges for both zips and images, so two builds of one commit can differ. Export a lock per artifact from uv.lock?
  2. Observability. Neither delivery mode wraps the process in opentelemetry-instrument. Add ADOT?
  3. Extra IAM for UpdateAgentRuntime. Untested; caller may need workload-identity or ECR read actions.
  4. Gateway id format. CI policy assumes gateway/<prefix>-gateway-*.

Documentation inconsistencies to resolve

  • 04-deploy-terraform.md and 05-deploy-boto3.md both say "No AWS deployment of this repo has been verified yet", but each ends with a "Verified run (2026-10-29)" section. 06-terraform-vs-boto3.md also says no deployment has been run and that the comparison isn't based on measured times, though 05 reports measured deploy/destroy times.
  • Docs 01, 02 and 09 describe carol's rejection as HTTP 403; both verified runs observed HTTP 401. The demo script accepts either, but the user-facing description should match.
  • 03-architecture.md states "Direct code deployment, so no Docker or ECR is needed" without the "by default" qualifier the patch calls for.
  • 10-ci-cd.md embeds a specific AWS account id and GitHub repository path. Consider parameterising before sharing the docs more widely.

Suggested review agenda

Identity & tenancy

How should customer identity bind to the caller? Claim-based customer_id in Cedar vs enforcement inside tools. What happens for staff acting on behalf of customers?

Trust boundary of the model

Which guardrails are prompt-only (no duplicate tickets, no invented data, no promises)? Which should move into tools or policy?

Skills as a supply chain

Skills in S3 change behaviour without code review gates. Who can write skills/? Should skills be signed, versioned per release or pinned per session?

Token passthrough design

Process-wide token relay plus per-sub agent rebuild: is it safe if a microVM ever serves more than one user? Is the lock adequate under concurrency?

Policy lifecycle

Ordering constraints (targets before policies), LOG_ONLY rollout, keeping VIEWER_TOOLS and Cedar in sync, testing policies in CI.

IaC strategy

Terraform as the system of record, boto3 as reference? Remote state, secret exposure in state, provider lag for AgentCore features.

Delivery model

Zip vs container as default for a team setting. Mode switch replaces runtimes; plan the cutover and session impact.

Operability

Tracing, alarms on policy denials, session idle timeouts and Runtime cost under parallel load, cold-start latency budget.

Reviewer checklist

  • ☐ Access control does not depend on model behaviour (verified by direct Gateway calls)
  • ☐ Business rules enforced in tools, with server-side re-checks on writes
  • ☐ Least privilege per role; confused-deputy conditions on trust policies
  • ☐ Secrets handling acceptable for target environment (TF state, .deploy/, CI secrets)
  • ☐ Skill-change process has an owner and review gate
  • ☐ Observability sufficient to investigate a wrong refund or a policy denial
  • ☐ Teardown and leftover checks are reliable for shared accounts
  • ☐ Documentation status statements match the verified runs
